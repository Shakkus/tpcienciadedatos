# Discovery — Las 4 V (casos ancla → NexoUrbano)

**Ciudad:** Buenos Aires · **Semilla datos sintéticos:** `67001` (`data/MANIFIESTO.txt`)  
**Escala de laboratorio:** 250 000 viajes, 80 vehículos, 6 000 lecturas, 120 riders.  
**Escala de diseño (una ciudad):** ~4 000 vehículos; los órdenes de magnitud de abajo usan esta hipótesis salvo que diga “repo”.

---

## 1. Netflix → recomendaciones de estaciones y pases

| Dimensión | Caso ancla | Transferencia a NexoUrbano |
|---|---|---|
| **Volumen** | ~3×10⁸ cuentas; telemetría de reproducción ~10¹¹–10¹² eventos/día; catálogo de títulos pequeño frente al video (PB almacenados). | Viajes ≈ “plays”: ~4 000 vehículos × ~6 viajes/día ≈ **2×10⁴ viajes/día** (~**10⁷/año**). Catálogo comercial (pases, recargas, accesorios): **decenas** de SKUs (`productos.json`). Repo: 250 000 viajes históricos. |
| **Variedad** | Billing estructurado; metadata de título en JSON; video y subtítulos binarios. | Viajes tabulares (CSV/Parquet: `ride_id`, estaciones, `duration_s`, `km`, `fare_ars`). Catálogo documental anidado (precio por ciudad, tags) → Mongo. Afinidad rider–estación–interés → grafo Neo4j (`grafo.json`). |
| **Velocidad** | “Seguir viendo”: segundos. Re-ranking de recomendaciones: batch horario/diario. | Recomendar pase o estación favorita: **minutos u horas** (Gold batch). Viajes: SLA **batch diario 06:00 ART** (`contratos/bronze_viajes.yaml`). No se exige < 5 s en personalización. |
| **Veracidad** | (1) Cuentas compartidas inflan watch time → entrenar por perfil, no por cuenta compartida. (2) Play sin stop → cerrar sesión por timeout. (3) Título visible pero sin licencia en el país → filtrar disponibilidad antes de rankear. | (1) Viaje fantasma (`duration_s` < 30, sin cierre) → **rechazo Silver** (reglas del contrato Bronze). (2) Rider sin aristas en el grafo → no inferir `LE_GUSTA`; solo recomendar con datos cargados. (3) Precio de pase de otra ciudad → filtrar por `ciudad` en Mongo antes del join a ventas. |
| **Complejidad** | Separar **catálogo** (documento de producto) del **grafo de afinidad** (quién consume qué). | Misma decisión: **Mongo = catálogo; Neo4j = relaciones** (`LE_GUSTA`, `SALE_DE`, `VIAJO_CON`). Spark Gold une agregados de viajes con salida de Cypher/Mongo para “qué pase venderle”. |

```
Volumen     → ~10⁷ viajes/año; catálogo O(10¹) documentos
Variedad    → CSV/Parquet (viajes) + JSON anidado (productos) + grafo (riders/intereses)
Velocidad   → personalización batch; ingesta de viajes diaria 06:00 ART
Veracidad   → viajes fantasma / precio por ciudad / grafo incompleto → contrato + filtros Silver
Complejidad → catálogo (Mongo) ≠ grafo de recomendación (Neo4j); Gold los cruza
```

## 2. Red social (X / Bluesky / Mastodon) → menciones, incidentes, sentimiento

| Dimensión | Caso ancla | Transferencia a NexoUrbano |
|---|---|---|
| **Volumen** | Firehose global X: orden **10⁸–10⁹ posts/día**; Bluesky/Mastodon: menor escala global; el squad consume **búsqueda**, no firehose. | Búsqueda de marca/hashtag en CABA: **10¹–10³ posts/día**; pico **~10⁴** en incidente (cobro, freno, batería). Offline en repo: `texto_ops.txt`, `app.log`, muestra de posts en Databricks. |
| **Variedad** | JSON de post (texto libre, autor, hora); imágenes y links; esquema de API que evoluciona. | API social (JSON) + tickets en texto plano (`texto_ops.txt`) + logs de app (`ride_start`, `payment_fail`) + eventos JSON en `data/stream/`. Sin esquema común con `viajes.csv`. |
| **Velocidad** | Crisis de marca: **minutos**. Sentimiento agregado para reporte: **batch diario**. | Poll API cada **1–5 min** (latencia aceptable < 5 min para alerta cualitativa). WordCount y cruce con facturación: **batch diario** con Gold. |
| **Veracidad** | (1) Bots y ráfagas → rate limit y dedup por `author_id`. (2) Sarcasmo → no usar sentimiento automático como KPI único. (3) Repost/borrado → dedup por `post_id`, ignorar edits sin id nuevo. | (1) Mismo término repetido en tickets generados → WordCount cuenta **término**, no clientes únicos; cruzar con volumen de viajes. (2) Mención “batería” en texto **no** reemplaza lectura de sensor → no escribir en Cassandra. (3) `payment_fail` duplicado en log → streaming con ventana 2 min + **watermark 1 min**; tardíos descartados en `gold_alerts`. |
| **Complejidad** | No joinear texto crudo fila a fila con viajes; **agregar primero** (término × hora × día). | Bronze: texto y logs tal cual. Gold: **top términos operativos** (`/nexo/gold/wordcount/`) + conteos por día; pregunta “facturado vs. cobro” une por **fecha**, no por `ride_id`. |

```
Volumen     → 10²–10⁴ menciones/día (búsqueda); no firehose
Variedad    → JSON API + texto plano + logs + stream JSON
Velocidad   → detección de pico de menciones < 5 min; agregados diarios
Veracidad   → bots/dedup / no confundir texto con telemetría / late events en streaming
Complejidad → agregación de texto antes del join temporal con viajes y ventas
```

**API social prevista (M3):** Bluesky `app.bsky.feed.searchPosts` o Mastodon hashtag `#NexoUrbano` (sin X de pago).

## 3. Sensores IoT → GPS, batería, temperatura

| Dimensión | Caso ancla | Transferencia a NexoUrbano |
|---|---|---|
| **Volumen** | Flota industrial: 10⁵–10⁸ lecturas/día según frecuencia (10–30 s) y cantidad de equipos. | Diseño: 4 000 vehículos × 1 lectura/15 s ≈ **2×10⁷ lecturas/día** (~**0,3–1 TB/año** JSON crudo; menos en Parquet). Repo: `lecturas_sensores.csv` (**6 000** filas) + `data/stream/*.json` para Structured Streaming. |
| **Variedad** | Series angostas: `device_id`, `ts`, métricas; poco cambio de esquema, mucho cambio de **calidad** y frecuencia. | Mismo patrón en CSV, JSON de stream (`ts`, `vehicle_id`, `event`, `battery_pct`) y tabla Cassandra. Clima (Open-Meteo): otra serie, grano por estación/hora → join en Silver (Databricks). |
| **Velocidad** | Posición y alarma: **< 1 min**. Histórico y SOH para planificación: batch. | Última lectura por vehículo: **segundos** (Cassandra `ts DESC`). Alertas `battery_low` / `payment_fail`: ventana **2 min**, slide **30 s**, watermark **1 min** (Spark Streaming). % clima adverso en viajes: batch Gold. |
| **Veracidad** | (1) GPS saltando (túnel) → descartar saltos imposibles entre puntos consecutivos. (2) Drift de sensor → no actuar con un solo punto bajo umbral. (3) Reloj atrasado → eventos tardíos fuera de ventana. | (1) Coordenadas fuera del bbox de CABA o salto incompatible con Δt → cuarentena; no actualizar `ultimo_gps` en HBase. (2) `battery_pct` ∉ [0,100] o caída abrupta de SOH → descarte; retiro de flota exige **2 lecturas** consecutivas bajo umbral. (3) Evento con retraso > watermark → **no** entra a `gold_alerts` (evidencia en demo). |
| **Complejidad** | Modelar **por consulta**: “últimas N lecturas de un vehículo”, no scan global por día. | **Cassandra:** PK `vehicle_id`, clustering `ts DESC`. Query “todas las lecturas de la última hora de toda la flota” es **anti-patrón** (mostrar error en M12). **HBase:** estado actual (`soh_bateria`, `ultimo_gps`) con rowkey que evite hotspot (ADR `003-hbase-rowkey`). |

```
Volumen     → ~2×10⁷ lecturas/día (diseño); 6×10³ en muestra repo
Variedad    → CSV + JSON stream + clima API; esquema estable, calidad variable
Velocidad   → < 1 min operaciones (Cassandra + streaming); histórico batch
Veracidad   → GPS imposible / umbral con 2 puntos / watermark descarta tardíos
Complejidad → time-series por vehicle_id (Cassandra); estado puntual en HBase
```

## Acta de squad — ¿Qué V es la más cara de “mentir”?

1. La **veracidad de telemetría y viajes** es la más costosa: un `duration_s` falso o una `battery_pct` errónea mueve dinero y manda técnicos al vehículo equivocado.  
2. El volumen de una sola ciudad entra en Spark batch; no es el cuello de botella del producto.  
3. La velocidad de menciones sociales tolera minutos; no compite con la batería en vivo.  
4. **Control 1:** rechazo Silver según contrato Bronze (`duration_s`, estaciones, `fare_ars`, orden de timestamps).  
5. **Control 2:** validación de sensores (rango batería, bbox GPS, dos lecturas para alerta de retiro).  
6. **Control 3:** watermark 1 min en streaming; documentar un evento tardío descartado en la demo.  
7. El WordCount de “cobro” no se interpreta como sentimiento sin cruzar con ventas del mismo día.  
8. El clima de Open-Meteo se trata como fuente externa: si la API falla, el join queda nulo y no se inventa código de clima.  
9. Owner acordado: contratos y Silver (Discovery); streaming alerts (Spark).  
10. Revisión al cierre de S1: docente valida que las tres fichas citen datos del generador, no definiciones de libro.
